DL-03 — From No UI to a User-Facing AI Layer
Betsy Autonomous Procurement Agent


0. Context

After DL-02 there were two working agent architectures — Pipeline and Orchestra — that could detect stockouts, flag duplicate invoices, and generate purchase orders. All of it was visible only in a terminal. Jenny, the operations manager this is built for, cannot read a Python stack trace. The agents were doing real work with zero visibility for the people who actually have to trust them. Nothing was user-facing, nothing explained what Betsy was doing or why, and there was no way for a person to approve or decline a decision. That is the gap this log closes.


1. Research question

How should Betsy present autonomous agent decisions to non-technical users in a way that builds trust and keeps a human in control?

3. What makes a good decision here

The interface has to do three things. It has to be usable by someone with zero technical background and no onboarding, because Jenny will not be trained on it. Every AI-generated element has to be clearly marked, so a user always knows what came from a person and what came from the machine. And it has to work as a layer on top of the existing procurement environment, not as a replacement for it — Betsy adds to the work surface Jenny already has, it does not ask her to abandon it.


4. What I decided

Build Betsy's UI on the enterprise AI-layer pattern — an AI command bar, an auto-generated narrative, AI-scored data tables, and inline approval cards — all served from the same server as the mock procurement environment.


5. Why this decision

Method: Library, Showroom

I started with Library research into how enterprise AI tools actually present AI to non-technical business users. The tools I looked at — Salesforce Einstein, Microsoft Copilot, Tableau Pulse, Glean, Notion AI — all follow the same pattern. The AI is a layer on top of a familiar work surface, not a separate app. Its output is short and actionable. And there is always a clear signal that separates generated content from human-entered data.

From that research I pulled four patterns that map directly onto what Betsy needs to show. An AI command bar gives a plain-language entry point, the way Glean and Copilot do. An AI narrative writes a short paragraph that explains the current state in plain English, the way Tableau Pulse narrates a KPI dashboard. AI-scored tables keep the standard data columns and add one generated column marked with a sparkle icon, the way sales-intelligence tools like Clari and Gong do. And inline approval cards put the human decision in the same surface rather than in a separate app.

Before touching any code I wrote the requirements down. The requirements doc captures the core design philosophy in one line: Betsy is a layer on top of the procurement environment, not a replacement. The language rules there are non-negotiable — no system jargon anywhere, Betsy speaks in the first person, and confidence is shown as dots rather than decimals. The reason is straightforward: Jenny has no technical background, and if she sees "trigger: stockout_risk, confidence: 0.87" she will stop trusting the system immediately.

[IMAGE: diagrams/wireframe-betsy-standalone.png — Version 1, the standalone dashboard direction: four screens — Home, Pending approval, Agent log, and the Supplier scoreboard. It reads cleanly, but it is a separate app Jenny would have to learn and keep open.]

From requirements I went straight to wireframing. The wireframes doc holds both versions. Version 1 was a standalone four-screen dashboard — Home, Approvals, Log, Suppliers. It looked clean but felt like a separate app Jenny would have to learn. Version 2 applied the enterprise patterns: one surface, an AI command bar at the top, an auto-generated summary card, and the existing procurement tables with AI columns added alongside the original ones. That is the direction I took.

The Showroom phase was building @wireframe — a fully interactive HTML prototype with working navigation, approve and decline buttons, expandable log entries, and a live badge counter. This let me validate the layout and the interaction model before touching the real dashboard.

[IMAGE: diagrams/wireframe-betsy-layer.png — Version 2, the chosen enterprise AI layer: a command bar to ask Betsy something, a plain-English summary of what Betsy just did, the inventory table, and the inline "Needs your OK" approval card — one surface, not a separate app.]

What I found is that the approval card matters more than anything else on the screen. The moment a user sees a card that says, in plain English, why Betsy stopped to ask instead of acting, they understand the whole system. Without that explanation the Approve and Decline buttons feel arbitrary. This is the same human checkpoint the before-and-after analysis puts at the heart of the TO-BE process: Betsy handles the routine work, and Jenny is brought in only for the high-value or unusual decision, with full context attached so the one-click approve or reject is an informed choice rather than a rubber stamp (@bpm_analysis).

What this means is that the approval card is not just a UI choice, it is the core trust mechanism. If the explanation is missing, people approve things they do not understand — which is worse than having no automation at all.

What I'd recommend:
For any AI tool aimed at non-technical users, lead with the reasoning before the action. Do not ask "approve this?" — explain what happened, what the agent would normally do, and why it stopped. Then ask. The confidence indicator should always be visible on the approval card, shown as dots rather than a decimal. Low confidence is exactly when you want a human involved, and the user should be able to see that that is why they are being asked.

GAP found:
The wireframe was interactive but static — it showed hardcoded data. The next step is wiring it to the live API and making Betsy actually run. That is what DL-04 has to do.


6. Does this hold up

- Usable with zero technical background: yes — no jargon anywhere in the UI, checked by reading every label out loud as if explaining it to a non-technical user.
- Every AI element clearly marked: yes — a sparkle marks every AI-generated column header, card, and narrative block, consistently across all four surfaces.
- Works as a layer, not a replacement: yes — @betsy and @index are two separate files served from the same server. The environment (@index) is unchanged; Betsy reads from and writes to the same API any human operator would use.

Assumptions I'm making:
Users read a visual sparkle as a meaningful "AI generated" signal. This is borrowed from how Notion AI and Copilot handle it, but I have not tested it with real users yet — worth validating in a later phase.

What surprised me:
The "layer, not replacement" framing resolved a lot of design questions on its own. Once I committed to Betsy not replacing the procurement system, decisions about what to show and what to hide became obvious. There was no need for a separate settings page, a user profile, or a navigation menu — because Betsy is not an app, it is a lens over existing data.


7. What this unlocks

Next LO stage: Realizing (DL-04 — wire the design to live data, pick a model, and test it)

What I can now do:
The design gives a clear target for implementation, because every UI component maps to a specific API endpoint. The narrative is computed from the inventory and agent-log endpoints. The Risk column comes from each SKU's stock-to-usage ratio. The Betsy Score comes from supplier reliability. The approval cards come from the approvals endpoint, and the Run Betsy button from a run-agent endpoint — the last two still to be built.

Ongoing monitoring:
The signal that this design works is not test coverage. It is whether Jenny can open the page and understand what Betsy did without asking anyone. That is the acceptance criterion for the UI layer.

How I'll know this worked:
Open @betsy after a pipeline run. If the narrative reads something like "Steel Bolts were running low — I ordered more from FastParts Co." and the inventory table shows that SKU marked critical with "ordered" in the action column, the design is doing its job.
