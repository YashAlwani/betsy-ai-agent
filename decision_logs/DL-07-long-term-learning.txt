DL-07 — Does Betsy Actually Get Smarter? Proving That Score Learning Changes Decisions
Betsy Autonomous Procurement Agent


0. Context

DL-06 proved that EMA scores update correctly. Given a known delivery event and a known baseline score, the formula produces the right number to four decimal places. That's a necessary condition for learning — but not a sufficient one. A score that updates correctly but never changes what gets ordered isn't learning, it's accounting.

The question that DL-06 couldn't answer: if QuickShip Express misses five deliveries in a row, does Betsy stop recommending it? And if FastParts Co builds a clean on-time record in the same period, does it move up the shortlist? The EMA formula is the mechanism. This DL is the proof of consequence — the test that connects score changes to actual procurement decisions.


1. Research question

How do I demonstrate that Betsy's supplier scoring actually changes what gets ordered — not just that numbers update, but that accumulated delivery history produces a different recommendation for the same problem?

3. What makes a good decision here

- Score trajectory must be mathematically predictable: 8 rounds of deliveries must produce values that match the EMA formula at each step
- The second pipeline run must receive different composite scores than the first — the ranked supplier list in evaluate.py must visibly reflect the delivery history
- If the learning is working, Betsy's recommended supplier for SKU-003 should change between run 1 and run 2


4. What I decided

Build a standalone integration test — @tests/test_long_term_learning.py — that runs two complete LLM pipeline calls with a structured delivery simulation between them. 8 delivery rounds: QuickShip Express receives 5 deliveries all 8 days late, FastParts Co receives 3 on-time deliveries. Both runs use the stockout_warning scenario on SKU-003, the same stockout that's been the main test case throughout the project.


5. Why this decision

Method: Lab

The test design was deliberate, not random. The delivery schedule was engineered to produce a clean, explainable reversal — the kind where the math is visible at every step and the conclusion is unambiguous.

The composite scoring formula in @pipeline/nodes/evaluate.py:

    composite = reliability_score / lead_days

At baseline:
    QuickShip  (SUP-003): 0.92 / 1d = 0.920   ← clear winner for SKU-003
    FastParts  (SUP-001): 0.95 / 2d = 0.475   ← second place

After 5 × 8-day-late deliveries for QuickShip (performance = max(0, 1.0 − 8 × 0.1) = 0.2):

    Round 1: 0.2×0.2 + 0.8×0.9200 = 0.7760
    Round 2: 0.2×0.2 + 0.8×0.7760 = 0.6608
    Round 3: 0.2×0.2 + 0.8×0.6608 = 0.5686
    Round 4: 0.2×0.2 + 0.8×0.5686 = 0.4949
    Round 5: 0.2×0.2 + 0.8×0.4949 = 0.4359

After 3 on-time deliveries for FastParts (performance = 1.0):

    Round 6: 0.2×1.0 + 0.8×0.9500 = 0.9600
    Round 7: 0.2×1.0 + 0.8×0.9600 = 0.9680
    Round 8: 0.2×1.0 + 0.8×0.9680 = 0.9744

Final composite scores:
    QuickShip:  0.4359 / 1d = 0.4359   ← second place
    FastParts:  0.9744 / 2d = 0.4872   ← new winner

The crossover happens between rounds 4 and 5. After round 4, QuickShip's composite (0.4949) is still above FastParts (0.4750). After round 5, QuickShip drops to 0.4359 — below FastParts even before FastParts improves. The 8-round schedule was chosen to make the crossover clear and reproducible with exact predicted values at each step.

The test runs with real LLM calls — evaluate.py asks the LLM to reason over the ranked supplier list and select the best option for the current stockout. The LLM sees the composite scores directly:

```python
ranked_info = [
    {
        "supplier_id": s["supplier_id"],
        "name":        s["name"],
        "score":       round(_score_supplier(s, sku_id), 3),  # composite
        "reliability": s["reliability_score"],
        "lead_days":   s["catalog"][sku_id]["lead_days"],
    }
    for s in ranked[:5]
]
```

Between run 1 and run 2, QuickShip moves from the top of that list (score=0.920) to below FastParts (score=0.436). The LLM receives a different ranking and is expected to produce a different recommendation.

Score trajectory confirmed from the first run:

```
#    Label                    Before     After    Perf
--   ----                     ------     -----    ----
1    QuickShip  8d late  #1   0.9200    0.7760     0.2
2    QuickShip  8d late  #2   0.7760    0.6608     0.2
3    QuickShip  8d late  #3   0.6608    0.5686     0.2
4    QuickShip  8d late  #4   0.5686    0.4949     0.2
5    QuickShip  8d late  #5   0.4949    0.4359     0.2
6    FastParts  on-time  #1   0.9500    0.9600     1.0
7    FastParts  on-time  #2   0.9600    0.9680     1.0
8    FastParts  on-time  #3   0.9680    0.9744     1.0
```

Every round matches the formula. QuickShip 0.9200 → 0.4359. FastParts 0.9500 → 0.9744.

Two bugs found during the first full run:

Bug 1 — approval filter too narrow: the original test looked for new approvals with action == "generate_po". The LLM in the decide node can also return "escalate" for an urgent stockout when it's uncertain about the right course of action — a valid response, not an error. An escalated approval is still queued, still has a supplier_id, but the filter missed it. Fixed by widening the search to any new approval for SKU-003, regardless of the specific action label:

```python
# before: only found generate_po approvals
return [a for a in pending
        if a.get("created_at", "") >= t_start
        and a.get("action") == "generate_po"]

# after: finds any queued approval for the target SKU
sku_matches = [a for a in approvals if a.get("sku_id") == sku_id]
```

Bug 2 — score preservation round-trip: the first implementation passed preserve_scores=True as a Python boolean query parameter through httpx to FastAPI. Python booleans in URL parameters don't always parse reliably across library versions. Fixed by adding PATCH /api/suppliers/{supplier_id}/score to @server/routers/suppliers.py and calling it explicitly in the test after each scenario injection — deterministic, no parsing ambiguity:

```python
def restore_scores(learned_scores: dict):
    for supplier_id, score in learned_scores.items():
        patch(f"/api/suppliers/{supplier_id}/score", reliability_score=score)
```

Both bugs were in the test infrastructure, not in the learning mechanism. The EMA formula worked correctly on the first run. Getting clean end-to-end evidence took one extra iteration.

The full behavioral comparison — which supplier did Betsy recommend in run 1 vs run 2 — requires the fixed test. The score evidence is solid and the composite crossover is proven. The LLM-facing comparison is the final step.


6. Does this hold up

- Score trajectory matches formula: ✅ — all 8 rounds confirmed from the first test run. QuickShip 0.9200 → 0.4359, FastParts 0.9500 → 0.9744. Every intermediate value matches the EMA formula exactly
- Second run receives different composite ranking: ✅ — after restore_scores(), GET /api/suppliers confirms learned scores are in place before run 2 fires. The ranked list in evaluate.py will show FastParts (0.4872) above QuickShip (0.4359) for SKU-003
- Supplier switch confirmed: 🟡 — composite crossover is mathematically proven and both pipeline runs complete. The approval-based supplier comparison is in progress — test infrastructure fixed, re-run pending

What I assumed: the LLM will weight the composite ranking when choosing a supplier. It normally does — the ranked list is the primary input to the evaluate node's prompt. But it's an LLM, and it also reads urgency, reasoning context, and lead time. If it decides that a 1-day lead time is the dominant factor for a critical stockout regardless of reliability history, it might retain QuickShip even after the score drops. That would be a valid and interesting finding — not a test failure. The composite formula says FastParts is better; the LLM might disagree and explain why. That disagreement would itself be evidence worth documenting.

What surprised me: the asymmetry between getting the mechanism right and getting the evidence right. The EMA math worked on the first try — every round produced the predicted value. The test had two separate infrastructure bugs that had nothing to do with the learning itself. Score updates, formula verification, and score preservation all worked. Capturing clean before/after pipeline decisions required extra debugging. The mechanism is more robust than the instrumentation.


7. What this unlocks

The full proof closes the learning story: every component works independently (DL-06 shows correct formula behavior in isolation), and the integration test shows the components combine into actual behavioral change across a realistic delivery timeline.

Not just "it runs" or "scores update" but "QuickShip delivered late 5 times, its score fell from 0.92 to 0.44, FastParts earned an 0.97 reliability score through consistent delivery, and Betsy changed who it ordered from."

That log is the audit trail for the learning claim.
