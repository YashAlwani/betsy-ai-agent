DL-01 — What Betsy Needs to Test Against: Building the Mock Environment
Betsy Autonomous Procurement Agent


0. Context

Project: Betsy — Autonomous Procurement Agent / ICT Bachelor Research Project, Phase 1

Why this matters right now:
I kept saying "I'm building an autonomous procurement agent" but couldn't picture what that meant in practice. What does a stockout look like as a data structure? What separates a suspicious invoice from a normal one? I couldn't answer any of that — and I couldn't test an agent against scenarios I hadn't defined. I needed to make the problem concrete before I could start solving it.

Where this fits:
Phase 1 (Architecture & Research). The GAP found here is what forces DL-02 to exist.


1. Research question

What environment do I need to observe, test, and validate autonomous procurement decisions reliably?


2. Current LO stage

[x] Analyzing — surveyed procurement failure modes, identified what data structures are required
[x] Advising — recommended building the test environment before touching agent code
[x] Designing — schema design for SKU fields, supplier tradeoffs, 4 injectable scenarios
[x] Realizing — built datasets, REST server, dashboard, and the scenario injection mechanism
[x] Managing — validated all 4 scenarios produce reproducible, resettable, non-bleeding results


3. What makes a good decision here

- Covers all 4 core procurement failure modes — if the environment can't produce all of them, I can't test the full decision space
- Data realistic enough to create genuine tradeoffs — not so obvious the agent always has one clear answer
- Fully resettable per scenario, so runs are reproducible and don't bleed into each other


4. What I decided

Build the environment first, agent second — mock datasets, a REST server, 4 injectable scenarios, and a live dashboard. All before writing a single agent node.


5. Why this decision

Method: Lab, Workshop

I built the inventory and supplier data first. Each SKU needed reorder_point and daily_usage_avg to make stockout math possible — without those two fields, the agent can't calculate urgency, just observe that stock is low (@inventory.json). The supplier data had to have real tradeoffs baked in: FastParts Co at "unit_price": 12.50, "lead_days": 2 vs BulkSupply Ltd at "unit_price": 9.80, "lead_days": 7 — cheap but slow, or fast but expensive. If all suppliers were identical, no decision logic matters (@suppliers.json). Designing that schema — what fields are actually required versus nice-to-have — was the first real design decision of the project.

Once the base data was in, I wired up the dashboard and looked at it live. I could see SKU-003 sitting at 45 units with 1.5 days of runway — and nothing in the system cared. The dashboard just showed the number. No alarm, no connection to the 5 suppliers in the next tab who could solve the problem in 24 hours (@app.py).

[IMAGE: gap-dashboard-empty-log.png — Dashboard showing Inventory Health tab with SKU-003 critical, Agent Log tab empty. The data exists, nothing acts on it.]

That gap pushed me to design the scenarios around failure modes, not the happy path. The stockout scenario was straightforward — drop current_stock to 45, push reorder_point to 200, and the math is undeniable. The expected outcome is baked into the scenario file itself: QuickShip Express, generate PO — so any agent run is immediately checkable against a known answer (@stockout_warning.json).

The duplicate invoice scenario was harder. It needed to be genuinely ambiguous — INV-2024-099 matches SUP-006 at exactly $1,470.00, same as two invoices already in the system. Fraud, or just a billing system that double-fired? That question forced me to realize early that this case would need LLM reasoning, not just rule matching (@duplicate_invoice.json). Stockout is math. Price spike is comparison. Duplicate invoice is judgment — three completely different cognitive operations, all living in the same environment.

[IMAGE: gap-supplier-scoreboard.png — Supplier Scoreboard showing QuickShip Express with lead time. Human can see the answer. Nothing connects it to SKU-003.]

The injection mechanism keeps scenarios isolated — apply_scenario() deep-copies the base state and patches only the relevant overrides, so every run starts from a clean baseline without restarting the server (@state.py:36-49).

What I'd recommend:
If I were advising a PM or operations lead on rolling out procurement automation — the first deliverable shouldn't be the agent. It should be this: a dashboard where you can see what "normal" and "critical" actually look like in your data. You can't trust an autonomous system to act on problems you can't yet see yourself. The 4-scenario test suite here should also be a non-negotiable acceptance criterion for any vendor selling procurement AI. If they can't demonstrate behavior across stockout, price spike, duplicate invoice, and supplier OOS — don't sign.

GAP found:
After all of this, the dashboard still just sits there. It shows the problem — SKU-003 critical, QuickShip Express available at 1-day lead. But nothing connects those two facts. No PO. No alert. A complete picture of a solvable problem with zero response. That gap is what DL-02 has to answer.


6. Does this hold up

- Covers all 4 failure modes: ✅ — all injectable, all have expected_agent_action for validation
- Non-trivial decisions: ✅ — supplier tradeoffs are real, duplicate invoice is genuinely ambiguous
- Resettable: ✅ — deepcopy(self._base) on every apply_scenario() call (@state.py:39)

Assumptions I'm making:
5 suppliers and 10 SKUs is enough variety for school-scope. Real procurement is noisier but the failure modes are identical.

What surprised me:
The asymmetry between failure modes wasn't obvious until I tried writing the expected_reasoning_contains fields for each scenario — and realized stockout, price spike, and duplicate invoice point at completely different cognitive operations. That asymmetry later drove the architecture decision in DL-02 directly.


7. What this unlocks

Next LO stage: Designing → Realizing (DL-02)

What I can now do:
Inject any of the 4 scenarios, observe real-time state in the dashboard, and validate agent output against a known expected result — without touching real data.

Ongoing monitoring:
This isn't just test infrastructure. In a real deployment, you'd run these same 4 scenarios against staging on a weekly cadence to verify the agent hasn't drifted. Same input, same expected_agent_action — that's your regression check. The dashboard becomes the monitoring layer a PM can open on a Monday morning without understanding a single line of agent code.

How I'll know this worked:
When the agent (DL-02+) logs a decision after the stockout run — trigger: stockout_risk, decision: generate_po, supplier: QuickShip Express. That's the moment the gap closes.
