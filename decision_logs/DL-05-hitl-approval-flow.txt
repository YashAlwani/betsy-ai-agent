Betsy Autonomous Procurement Agent

3. What makes a good decision here

- A decision queued by the pipeline must appear as a card in betsy.html without Jenny doing anything
- Clicking "Yes, go ahead" must produce a real PO in the procurement environment — visible in index.html immediately
- Every approval and rejection must be recorded so the audit trail is complete


4. What I decided

Build /api/approvals as a standalone router with three endpoints (GET pending, POST approve, POST reject), have act.py queue every requires_human decision to it, and execute the deferred PO creation inside the approve handler directly against state.


5. Why this decision

Method: Lab

The implementation question was where to put the execution logic when a human approves. Two options: re-run the pipeline from the saved decision, or store the PO payload at queue time and execute it when approved. Re-running the pipeline would mean another LLM call and another 30-second wait just to place an order the agent already decided on. Storing the payload at queue time is simpler and more predictable — the PO is pre-built, the approve endpoint just pulls the trigger.

@pipeline/nodes/act.py builds the complete PO payload the moment a decision is made — supplier, SKU, quantity, unit price, reasoning — and passes the whole thing to the approval queue. Nothing is recomputed later. The approve endpoint in @server/routers/approvals.py picks that payload up, creates the PO directly in state, and logs the human decision.

betsy.html needed zero changes — it was already calling GET /api/approvals, POST /api/approvals/{id}/approve, and POST /api/approvals/{id}/reject. The frontend was waiting for the backend.

![betsy.html approval cards — "Needs your OK" section showing two pending items: flag_duplicate for SKU-004 and generate_po for SKU-003 at €11,325, with confidence dots, reasoning, Approve and Decline buttons](./images/dl05-approval-cards.png)

The Lab phase was running 11 test cases against the live server: empty queue at start, inject scenario, trigger pipeline, check queue populates, reject one item, approve the other, verify queue empties, verify PO was created, verify both decisions appear in the agent log, then guard cases for double-resolve (400) and unknown ID (404). Full results in @docs/test-report-dl05.md.

```
T1  GET /api/approvals before run         → []                          ✅
T3  GET /api/approvals after run          → 2 pending items             ✅
T5  POST .../approve on generate_po       → {"po_id": "PO-20260531-..."}✅
T6  GET /api/approvals after both resolved→ []                          ✅
T7  PO in /api/purchase-orders            → requested_by: betsy-human-approved ✅
T9  Re-approve resolved item              → 400                         ✅
T10 Approve unknown id                    → 404                         ✅
```

What surprised me: the test showed the queue was empty after a pipeline run even though the queuing code was correct. Traced it to @server/state.py:reset() — one line was wiping self.approvals at the end of every pipeline run, included when wiring up the reset flow. Approvals aren't mock data that resets between scenarios — they're user-facing decisions that live until Jenny acts on them. Removing that single line fixed it.

![betsy.html decision log section after approving — showing ✅ You approved (SKU-003) and ❌ You declined (SKU-004) entries with timestamps](./images/dl05-decision-log-after.png)

What I'd recommend: store the full decision payload at queue time, not a reference to recompute it. If you defer execution until approval and recompute, you introduce a second LLM call, potential state drift (prices may have changed), and complexity you don't need. The pattern — decide early, store payload, execute on approval — is how most approval systems work for exactly this reason.

GAP: approvals live in memory. A server restart wipes the entire queue. If Jenny has a pending $11k PO and the server goes down, it's gone — she never sees it again. That's what DL-06 needs to close.


6. Does this hold up

- Cards appear in betsy.html without manual action: ✅ — betsy.html polls every 5s, new approval items show up within one poll cycle after a pipeline run
- Approve creates a real PO: ✅ — PO-20260531-0E74 created with requested_by: betsy-human-approved, visible in index.html orders tab in real time
- Full audit trail: ✅ — every approval and rejection logs to /api/agent-log with decision_id and action. The decision log section in betsy.html shows human_approved and human_rejected in plain language

Pending approvals have no expiry. If a stockout approval sits pending for three days, the stock situation has probably changed — prices may have shifted, the supplier might have gone OOS. There's no mechanism to surface "this approval is stale." @pipeline/nodes/act.py doesn't store a created_at comparison against current data. Worth adding a staleness warning in a later pass.

The queue_approval() call in act.py is a synchronous HTTP call back to the same server. It works because uvicorn handles concurrent requests, but it means the pipeline has a hard dependency on the server being up and reachable at localhost:8000. If the server isn't running and someone triggers the pipeline directly from the terminal, the approval silently fails and the decision is lost. @shared/api_client.py swallows the error. That's fine for now but worth hardening when persistence comes in.

What I assumed: Jenny will act on approvals in the same session. This assumption breaks the moment she closes her laptop.


7. What this unlocks

Next LO stage: Managing — ongoing monitoring of the approval queue, decisions surviving restarts

What I can now do:
- Run any scenario from betsy.html, watch approval cards appear, approve or decline them, and see the result in the procurement environment in real time
- The full loop — detect → decide → escalate → human approves → PO created — works end to end without touching a terminal
- The audit trail exists: every decision is logged, every human action is logged

Ongoing monitoring: the agent log is the health check. After a run, look for human_approved or human_rejected entries in betsy.html's decision log section. If a run produces pending_human_review actions but no approval items appear, the queue_approval() call is failing silently — check that the server is up and reachable from the pipeline thread.

How I'll know this worked: run stockout_warning, see the approval card appear in betsy.html within 5 seconds, click "Yes, go ahead", watch "✅ You approved" appear in the decision log and the PO appear in index.html's orders tab. One uninterrupted flow. That's the moment.
